# 다운로드 의존성·로그 표시 (#190)

진행 상태는 기존 설정의 기본 300ms 간격으로 묶어 반영합니다. 이 변경은 각 배치에서 만드는 화면 행을 제한합니다. `groupDownloadItems`의 O(n) 인덱싱과 전체 목록 기준 완료/실패 집계를 유지하며, 로그 내용이나 같은 문구의 재시도 사건을 제거하지 않습니다.

## 화면과 상태

- 의존성 모드는 그룹을 10개씩, 각 그룹의 하위 항목도 10개씩 표시합니다. 두 페이지 번호는 독립적이며 모든 그룹과 항목에 접근할 수 있습니다. 원본 데이터의 순서는 유지합니다.
- 그룹은 기존처럼 처음 펼쳐집니다. 이후 사용자의 접힘 상태와 그룹별 하위 페이지는 진행 갱신 및 그룹 페이지 이동에도 유지됩니다. 닫힌 그룹의 행 DOM은 닫힘 애니메이션 후 제거합니다.
- 그룹의 전체/완료/실패 수는 현재 페이지가 아닌 전체 패키지 기준입니다. 실패한 부모·하위 항목의 오류 상세와 재시도 버튼은 해당 항목으로 연결됩니다. 변경된 callback과 최신 항목 객체도 그대로 전달합니다.
- 로그는 시간/내용/상세/순서를 보존하며 50개씩 표시합니다. 이전 페이지를 보는 중 새 로그가 추가돼도 페이지를 옮기지 않습니다. 최신 로그는 마지막 페이지에서 확인합니다. 초기화나 목록 축소 때 유효한 페이지로 보정합니다.
- 의존성 하위 행과 로그 행은 객체 참조가 같으면 다시 렌더하지 않습니다. 로그 카드도 memo로 분리하며 진행/결과 화면의 style 객체를 고정해 로그 배열이 같은 바이트 진행 갱신에서 카드를 재처리하지 않습니다. 데이터 저장과 기존 store 구독 구조는 유지합니다.
- 일반 표는 **진행 화면의 10행 페이지화**, **완료 화면의 `paginate={false}` 전체 표시**를 유지합니다. 의존성 모드의 페이지화는 두 화면 모두 적용합니다.

전체 집계에 필요한 O(n) 순회는 남습니다. 모든 목록 처리를 제거하거나 전체 앱 갱신 비용을 없애는 변경이 아닙니다. 로그 자체의 보관량도 줄이지 않습니다.

## 재현과 측정

```bash
node scripts/profile-download-lists.mjs c72a765 /tmp/download-list-profile
```

앱 빌드/설치 없이 독립 fixture만 메모리에 번들링합니다. production React 19.2.3, Chromium 143.0.7499.4, macOS 26.3 / Apple M4 arm64에서 2026-09-28 실행했습니다. HMR/StrictMode/Profiler 없이 `flushSync` 앞뒤의 render/commit 시간과 별도 layout 구간을 기록합니다. 각 조건은 새 페이지에서 3회 실행합니다.

표 fixture는 1,000개 항목의 첫 하위 항목만 새 객체로 교체하며 나머지 참조를 보존합니다. 의존성 모드는 루트 1개+하위 999개입니다. 로그 fixture는 같은 logs 배열과 고정된 style을 유지해 부모의 진행 갱신을 재현합니다. 실제 제품의 두 호출부도 style 참조를 고정했습니다. 각각의 초기 렌더 시간, 갱신 시간, DOM 수는 결과 JSON에 구분해 저장합니다.

| 조건 | 기존 갱신 3회(ms) | 변경 갱신 3회(ms) | 기존 → 변경 DOM 요소 |
|---|---|---|---|
| 의존성 1,000개 | 155.6 / 153.4 / 156.4 | 1.9 / 1.9 / 1.9 | 22,067 → 330 |
| 진행 일반 표 1,000개, 10행 표시 | 4.9 / 5.5 / 5.1 | 5.3 / 4.9 / 4.9 | 347 → 347 |
| 완료 일반 표 1,000개 전체 표시 | 189.4 / 173.3 / 176.0 | 181.4 / 176.9 / 182.8 | 25,059 → 25,059 |
| 같은 로그 1,000개 | 51.4 / 53.2 / 51.1 | 0.1 / 0.0 / 0.1 | 9,028 → 512 |
| 같은 로그 5,000개 | 270.2 / 265.7 / 269.9 | 0.1 / 0.3 / 0.0 | 45,028 → 512 |

의존성 하위 행은 999→10개, 로그 DOM 행은 50개입니다. 로그 초기 렌더도 전체 보관량과 무관하게 50개를 만들며, 5,000개 fixture의 초기 render/commit은 338.0–342.7→25.9–26.0ms였습니다. 0.0ms 표기는 브라우저 타이머 해상도에서 측정된 값으로 비용이 절대 없다는 뜻은 아닙니다.

이 값은 독립 컴포넌트 fixture 결과입니다. 표와 로그 시간을 합산해 전체 화면 CPU라고 주장하지 않으며 사용자 평균·전체 Electron 앱·모든 OS 성능으로 일반화하지 않습니다. 완료 일반 표의 대량 전체 표시는 여전히 비용이 크며 이번 변경의 개선 수치에 포함하지 않습니다.

## 검증

`download-lists.test.tsx`는 실제 Ant Design 컴포넌트에서 표시 행 제한, 끝 페이지 접근, 전체 집계, 부모/하위 재시도 및 오류 상세, 페이지·접힘 상태, 로그 중복/상세/순서와 초기화를 검사합니다. 항목 내용 getter를 관찰해 변경 없는 하위 행·로그 내용을 다시 읽지 않는지도 확인합니다. 기존 `utils`, `resolved-items`, `download-store`, `use-download-page-controller` 테스트로 그룹 귀속·배치·재시도 결과를 함께 확인합니다.

브라우저 재현은 마지막 의존성 페이지의 재시도 대상과 마지막 로그 접근을 확인하고 캡처를 저장합니다. 시각 검토는 1280×900에서 처음/마지막 의존성 페이지와 5,000개 로그 화면을 대상으로 했습니다. 실제 외부 다운로드나 전체 앱 CPU 측정은 포함하지 않습니다.
